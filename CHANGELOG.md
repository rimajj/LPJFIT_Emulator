### Fixed
- **The size limit on the three work-stream status files had been switched off without anyone meaning to, and two requested code changes were lost behind it.** Each stream keeps one status file, capped at 120 lines so it stays readable and gets pruned. Streams also send each other messages, which land in that same file. Since 10 September those messages were not counted against the cap — for a good reason: a message costs eight lines whatever it says, so counting it immediately turns the recipient's build red for something they did not do and may not see for days. But the exemption never expired, and nothing else ever removed an old message. The data stream's file reached **436 lines against a limit of 120**, of which 338 were 17 old messages, and every automated check called it clean.
- ⚠ **The real cost was not the file size.** Two of those unread messages were one-line requests from the training stream to the data stream, and both said explicitly that they had to be made *while* the training data set was being rebuilt, because they get much more expensive afterwards. The rebuild ran on 15 September — 6,000 simulations — and neither request was included. Both were checked in the actual source code rather than taken from a write-up: the four soil-property columns are still absent, and a forest-free grid cell still records its species mix as "0 % of each" instead of "not applicable". The second of those is currently patched over wherever the data is read, by four separate places that each have to remember to do it.
- **Messages are now free for two weeks and counted after that.** The protection that the exemption was written for is kept exactly — nobody's build breaks because someone messaged them. After two weeks the message is either dealt with (filing it away takes seconds) or it is not, and that is the thing worth failing a build over. Two weeks is not a new number: it is the horizon the filing tool already recommends in its own instructions. Measured across the three files: everything passes today, the data stream's file fails on 25 September, and all three fail by 2 October — so each stream is prompted to clear its own backlog rather than waiting for someone to notice.
- ⚠ **Neither lost request is acted on here, on purpose.** Both change what the data-preparation code produces, and the training stream's own message warns that one of them alters previously generated tables if they are ever regenerated. Making either change now would leave the 6,000-row data set that is already saved, fingerprinted, and being used disagreeing with the code that produced it. Choosing between regenerating it and accepting that mismatch costs real compute time and is not a call to make in passing, so it is reported instead.
- **Messages sent from the integration branch were signed "from line ?".** The sending tool worked out who was sending from the branch name and quietly gave up on anything that was not a work stream, so six messages sent on 16 September cannot be replied to and do not say who wrote them. The integration branch now identifies itself, and an unrecognised branch is refused with a request to name the sender rather than sending an anonymous message.

### Added
- **The acceptance test can now judge quantities that live near zero.** Tolerance here is a percentage of the true value, which works for quantities like biomass but collapses for a share: a tree type that makes up 0.2 % of a forest's stems gets a tolerance of 0.02 %, and nothing can land inside it — not the emulator, and not a second run of the simulator being emulated. The test now also carries a minimum tolerance in the units of the quantity itself. **The value is measured, not chosen:** it is how much the simulator disagrees with itself, from one run to the next, in 90 % of cases — 0.0384 in share units, against a typical disagreement of 0.0027. Raising such a threshold after seeing the results is not a threshold, and the code says so beside the number.
- ⚠ **It deliberately has no default value, and every place that computes a tolerance now has to say which one it wants.** A minimum expressed in *shares of stems* is meaningless for soil carbon and merely wrong for leaf area, so a default would quietly apply a figure measured for one quantity to every other. The five existing places all ask for none, which reproduces every previously published number exactly — checked to the last bit, not approximately, and locked down by a test so that adding a convenient default turns the suite red.

### Changed
- **The integrator may now do any work stream's work directly, on the owner's instruction.** The project is split into three streams — data, training, experiments — each with its own branch and its own folders, so that two of them editing at once cannot collide. That split was never meant to fence off the integrator, and in the actual checks it never did.
- ⚠ **The rule that said otherwise had never been enforced, and that is the part worth reporting.** The greeting printed at the start of every integration session stated that work belonging to a stream "does not belong here" and would be refused. That was a specific claim about what the automated checks do, and it was false: the checks identify which stream you are by which branch you are on, and on the integration branch there is no stream, so the rule cannot fire. Verified before changing anything, by making exactly such an edit and running the check, which passed. **So the cost was never a blocked change — it was sessions that never attempted one**, and handed the work back to a stream instead. A start-up message that asserts a refusal works just as well as a real refusal, and is cheaper to get wrong, because nothing tests a greeting. The three places that describe this — the greeting, the runbook, and the ownership map — now agree with each other and with the code.
- **Three rules are deliberately kept**, and they are about evidence rather than territory: a decision record that has been accepted cannot be edited, a sealed experiment plan cannot be edited, and the job and results ledgers can only be appended to. Each exists so that a past result cannot be quietly improved after the fact, and none has ever blocked work, because writing a new record that supersedes the old one is always available.

### Fixed
- **Three published results stated their setup wrongly, and now say so in the same paragraph.** Each described the simulations behind it as run at constant carbon dioxide. They were not: the 1,000-year warm-up runs against a changing carbon dioxide record, so its last 300 years carry the real historical rise of about a third. Two of them additionally said the warm-up "had not settled", which was withdrawn in September — that apparent drift was the response to rising carbon dioxide, and with it held fixed the curve is flat.
- **No result changes, and the reason is worth stating.** Every run in the set shares the identical carbon dioxide path, so it is the same for every comparison and cannot favour one over another. What the error genuinely breaks is the word *equilibrium*: what these results describe is the forest the standard warm-up reaches *through* the historical carbon dioxide rise, not the forest a climate would eventually support. Re-running them against the newer set built with carbon dioxide held fixed remains outstanding.
- **The correction is attached to the wrong sentence rather than filed elsewhere**, so the mistaken claim cannot be read without it. The original sealed plans keep their original wording and were deliberately not edited — they are the record of what was promised in advance, and editing them after the fact would destroy the thing that makes them worth having.
- **All 40 outstanding job records are closed, each checked against the runs themselves rather than against a document.** These record every computation sent to the cluster, and stay open until somebody confirms the results arrived; from 22 September an unclosed one would have blocked every merge. None had been closed, because results land hours or days after the session that launched the work has ended, and the next session belongs to whoever picks it up. Every one of the 6,602 forest simulations reports success in its own log, and the two result tables hold exactly the 6,000 and 600 rows claimed for them. Not one was closed on the strength of a write-up.
- **A record of provenance accepted a value that was not one.** Closing these, a fingerprint of a result file was recorded that had the right first 16 characters and an invented remainder, because only a shortened form had ever been displayed. Nothing rejected it — the length alone would have. The tool now checks, the wrong entry is superseded by one that says plainly what was wrong with it, and no measurement had depended on the value.

### Added

### Fixed
- **The safety check that runs before every commit had a documented "let me through anyway" switch that had never once worked.** The check runs the project's own rules over the files about to be committed, and when it refuses it prints the way to override it deliberately — which leaves a visible reason line in the commit that the build then counts and reports. But the override was written as something you type in front of the command, and this kind of check cannot see anything typed in front of the command; it only sees the command itself. So the check could not be switched off at all, while telling you how to switch it off. The same fault in the sister check that guards the shared login machine was found and fixed on 8 September; this third one, in the file next door, was missed by that fix and has been broken ever since. If it failed, it printed exactly what it prints when there is nothing to report. There are 38 such jobs outstanding right now. Both reports now say plainly when they could not run.

### Changed
- **Correction to an earlier entry in this section: "the 1000-year spin-up has not converged" was our error, and it is withdrawn.** The model's own run-in period ends with three centuries driven by the real historical rise in atmospheric CO₂, and what the earlier measurement read as the forest still drifting upward was the forest responding to that rise. What the earlier entry did get right is that the stored state is not an equilibrium: it is a forest still adjusting to a CO₂ step, which is why a second training set was built with CO₂ genuinely held fixed. The withdrawn entry is marked where it stands rather than deleted. Written up in `docs/decisions/20260915-D-the-spinup-did-converge-the-late-rise-is-transient-co2.md`.

### Added
- **The safety checks are now tested against commands nobody wrote by hand.** Ten times now, one of these checks has judged text that is not the thing it was guarding, and nine of those were found by somebody being blocked in the middle of their work, after every automated check had passed — because a list of test cases somebody thought of cannot contain the case nobody thought of. The new test builds its commands out of this project itself: its own paragraphs, its own files, its own commit messages, wrapped in forms that run nothing at all, so a refusal is by construction a mistake. It found both of the faults above in a single run. Its own first draft was wrong in an instructive way — it fed the file contents to the check as if they were the command — which was caught by asking whether the failing test failed for the reason it claimed.

### Fixed
- **Two ways the login-node safety check refused commands that run nothing are now fixed, on the owner's decision.** The check stops heavy computation being started on the shared login machine by deciding whether a command could run a program. **First:** writing a file by typing its contents straight into the command — the ordinary way to create a script or a note — was refused whenever those contents contained an odd quotation mark, because the check tried to read the file's *contents* as though they were shell instructions, could not, and defaulted to refusing. Twelve of this project's own 178 files could not be written back this way, including the check's own source file and two work streams' state files. It now works out where the file's contents begin without trying to parse them, and if it genuinely cannot tell, it still refuses. **Second:** six everyday commands that only print or move about — printing a line, changing directory, testing whether a file exists — were not on the list of things that cannot run a program, so appending any of them to an ordinary read ("count the lines in this file, then print done") turned the whole thing into a refusal. Eight of ten such commands were refused; the two that got through did so only because of where a semicolon happened to fall, which is luck, not safety.
- **Measured before and after on three bases**, because a safety check that has been loosened needs evidence and not an argument: of the 1,312 distinct commands this project's sessions have ever issued, 41 were refused before and 32 after, and every one of the nine that changed runs nothing. Everything the test suite requires to stay refused still is, including handing a file's contents to something that *can* execute them. The full suite passes, 306 checks.
- ⚠ **The transcript record shows the habit this was meant to prevent had already started.** Two past sessions got past the check by splitting a word in half inside quotation marks so it would not be recognised. That hides the defect from whoever would fix it, and all three work streams have been asked to report such refusals instead.

### Fixed
- **The fix below contained a fresh instance of the exact fault it was fixing, and it was caught by being blocked by it.** Minutes after that change went in — tested, committed, and passing every automated check — sending an ordinary internal message to another work stream was refused as heavy computation. It runs nothing. The message quoted the before-and-after table from the write-up, which contains an example of the "message starts here" marker; the new code searched the plain text of the command for that marker, found the one that was merely being *quoted*, and treated everything after it as message rather than command. That cut the command in half, left a quotation mark unclosed, and the check then fell back to its safe default of refusing. The repair is to ask the command reader whether a real marker is present before letting any text-matching near it — a marker inside a quoted piece of text is part of that text and never comes back as a real one. The refused message was re-sent afterwards and went through, which is the check that mattered. **The wider point is where it was caught:** the earlier fault in this same change was caught by reading the change, but this one survived that and every automated check, because a test suite of hand-written commands cannot contain the command nobody has written yet — and the one that broke it was a message *about* the fix. A change to a safety check is not finished when its tests pass; it is finished when it has been used.
- **A semicolon in a commit message no longer gets the commit refused.** The safety check that stops heavy computation being started on the shared login machine works by deciding whether a command could run a program. To do that it chopped the command at the punctuation a shell uses to join commands together — but it did that on plain characters, so it could not tell a real separator from the same character sitting inside a piece of quoted English. A message containing "…ran twenty hours ago; the result is on the main branch…" was read as two commands, the second beginning with the word "the", which is not a program it recognises, so the commit was refused. A search whose pattern contained a vertical bar failed the same way. Both now work. The check now splits the command at real separators rather than at characters, and text handed to a command that cannot execute it — a commit message given to the version-control tool — is treated as what it is, data. Text handed to something that *can* execute it keeps being treated as a program and is still refused. **This was applied on an explicit decision by the owner.** It had been diagnosed and deliberately left unapplied the day before, because relaxing a safety check is not something to do on one's own initiative, however good the argument.
- **Checking that fix turned up a third fault that nothing had yet hit.** When the check set a commit message aside, it then re-read the command from the beginning, saw the same "message starts here" marker a second time, found no second end-marker, and swallowed everything after the first one as though it were more message — including, in principle, a real second command tacked on the end, which would then have gone unexamined. Found by reading the change rather than by being blocked by it, fixed, and added to the list of commands the test suite requires to stay refused.
- Every command the suite requires to stay refused still is, including all five it singles out as the ways an earlier version of this check could have been opened up — among them running a program from a quoted string, and hiding one behind an innocuous-looking command. Both new behaviours are pinned in both directions: what must be allowed, and what must be refused. The full test suite passes, 294 checks.
- Two further commands were added to the "must be allowed" list that this change did **not** repair — they already worked, and are there because this change could have broken them. They are filed separately from the three genuine repairs, on the grounds that a test case filed under a fault it never demonstrated makes a suite look stronger than it is.

### Fixed
- **Diagnosed, not yet fixed: a semicolon in a commit message gets the commit refused.** The safety check that stops heavy computation being started on the shared login machine reads the command text, decides whether it could run a program, and refuses if it could. To do that it chops the command at the punctuation the shell uses to join commands together — but it does this on plain characters, so it cannot tell a real command separator from the same character sitting inside a piece of quoted English. A commit message containing "…twenty hours ago; the result is on the main branch…" is therefore read as two commands, the second of which begins with the word "the", which is not a program the check recognises, so the commit is refused. The same thing happens to a search whose pattern contains the vertical-bar character. This is the eighth time in this project that a safety check has been caught judging text that is not the thing it is supposed to be guarding, and the second and third times for this particular file — which was itself written to stop exactly that. Both were hit today during ordinary work. **A fix was written and checked against every case the test suite pins, and deliberately not applied.** Relaxing a safety check is not something to do on one's own initiative, however good the argument, and the tooling refused the edit for that reason. It needs a decision. The full diagnosis, the evidence, and the proposed change are in `docs/decisions/20260916-INT-the-command-lexer-resplits-prose-on-shell-operators.md`. **Until then, the way through is to put the message in a file** and pass the file's name (`git commit -F <file>`) rather than switching the check off. A file name contains no English. Switching the check off works too, and is worse: it teaches the habit of disabling a safeguard on commands it was never meant to catch, and that habit does not reliably stop at the harmless ones.

### Added
- `scripts/corpus_pilot.py --const-co2` and `corpus_spinup_config.write_constant_co2`, which pin CO₂ by writing a single-value forcing file. Done that way, rather than with the model's own climate-fixing switch, because that switch also replaces the weather sequence — and rather than by shifting the run's calendar, because that would silently convert 30 real weather years into 30 more randomly drawn ones. Details and the source lines: `docs/reference/corpus-design.md`.
- **A second run of the same forests with a different random draw, so the model's own noise under a changed climate can be measured instead of guessed.** `scripts/corpus_pilot.py --seed N --subset M` reruns a subset of the pilot's cells and climates with only the model's random seed changed. It reuses the first run's climate files byte-for-byte rather than rebuilding them, so the difference between the pair is the model's own randomness and nothing else. 20 cells x 30 climates = 600 spin-ups, about 67 core-hours, against the original pilot's 670. This is the measurement five open questions were waiting on. The project's acceptance rule is "within 10 %, or within the model's own run-to-run disagreement, whichever is wider" — and that disagreement has only ever been measured on today's climate, where it comes out at almost exactly 10 %, i.e. no wider than the floor. Nobody has ever measured it on a forest driven to a warmer climate, which is the case the whole project is about.

### Fixed
- **The spin-up was never run at constant CO₂, and fixing it removes about a quarter of the forest's carbon.** The model's CO₂ input is a file of real year-by-year values from 1700 onward, and the 1000-year spin-up runs model years 1000–1999 — so its last 300 years were driven by the actual industrial-era CO₂ rise, +32.8 %. Rebuilt with CO₂ genuinely held fixed (corpus `v2-constco2`, 6,000 runs, all completed), the same 200 locations under the same 30 climates hold **24 % less vegetation carbon**, 25 % less above-ground biomass and 21 % less leaf area, with 4 % more stems — a younger, lighter forest. The number of locations with no trees at all is unchanged, 380 of 6,000.
- **So "the 1000-year spin-up never settles down" was wrong, and it was our error.** Under fixed CO₂ the forest is flat to **0.15 % per century** from year 200 on; the 6.5 % per century previously reported is the CO₂ response, and the trend was measured over a 200-year window lying entirely inside the CO₂ rise. Found by the owner asking why one location showed no late increase — it does not, because the dense forests that hold most of the carbon are flat or shrinking and the increase is concentrated in sparse ones.
- **The wording that hid it was "untouched".** Every corpus build recorded that CO₂ was "untouched and never written", which was true and is not the same claim as "constant". Both the code comment and the provenance file now state which of the two they mean.
- **No previously reported score is affected.** Every run of a given corpus shares the identical CO₂ path, so it cannot bias a comparison between climates — the warming-response and species-mix results stand. What it breaks is calling the result an equilibrium.
- **The subset picks evenly spaced cells, not the first N.** The cell list is ordered south to north, so "the first 20 of 200" put every cell between 52 S and 27 S — one temperate band, no tropics and no boreal — and the quantity being measured is known to be largest in sparse forests. Caught by inspecting the first planned run; the replacement spans 52 S to 66 N across 20 separate regions. `tests/test_pilot_replicate.py` pins this, along with the two other ways a replicate can silently measure nothing: moving the original run's file paths, or rebuilding its climate inputs instead of sharing them.
- **A build that writes no climate files now says its no-op check did not run**, instead of reporting "all pass" over zero files checked. A check that cannot fail reads exactly like a check that passed.

- **Four candidate cheap repairs of the height heads, all measured and all rejected**, which closes post-hoc repair as a route. - **The synthesised roster contained no tree above 13.3 m anywhere in the block, while the truth reaches 25.8 m — and those missing tall trees were the entire leaf-area shortfall.** The predicted quantiles are CELL quantiles (`corpus/state.py` pools all 25 patches before taking a percentile), but the roster was drawn inside each patch from `u = (arange(n) + 0.5) / n` with n ≈ 19. Every patch therefore received the same nineteen ranks, spanning 0.026 to 0.974, and the cell received twenty-five copies of one truncated ladder. A stand's tallest tree lives near rank 0.998, so it was unaddressable in every cell, however good the prediction — the donor pool held 794 admissible stems above 16 m reaching 30.3 m, and the predicted 90th-percentile height was good to 7 %. The true state holds 308 stems in 16–20 m and 72 in 20–25 m; the synthesised file held none, and those two empty classes account for 109 % of the leaf gap. Ranks are now drawn once across the cell and dealt to patches at random, so each patch is a random SAMPLE of the stand rather than a copy of it.
- **And three knots joined by straight lines cannot make a forest.** Cell-level ranks alone recover almost nothing: continuing the p50→p90 slope past the top knot reaches 14.3 m at rank 0.999, still 9 m short of the real tallest tree. The distributional SHAPE now comes from the template cell's own stems, recalibrated onto the three predicted knots, so only location and spread are the emulator's. This extends the mechanism `type_ladder` already used for tree type to the matched traits — one real stem per rank, read whole, so the template's joint height–density structure survives instead of two marginals being recombined at perfect rank correlation.
- **The previous record's proposed fix is rejected, on the model's own source.** It was to rescale each stem's leaf carbon to the predicted cell total, on the reasoning that leaf carbon is an untargeted per-stem mass. It is not: `tree/allometry_tree.c:39-41` derives height from it as `k_latosa * sapwood / (leaf * sla * wooddens)`, so multiplying leaf carbon by the 1.41 the prediction asked for would have divided every tree's height by 1.41 at the first allocation.
- **The emitted restart file's roster was valid stem by stem and not viable as a forest, and that — not the synthesis — is what halved its carbon.** Donors were chosen by nearest height and wood density over a pool deliberately spanning biomes, and the tree TYPE was never looked at, so 31 % of the stems written into a block of twenty temperate European cells were tropical broadleaved evergreen: a type those cells' own real state never contains. Half the roster and two thirds of the carbon went with them. Tree type is now COPIED from the target cell's own template roster at the matching size rank, and the trait match happens only among donors of that type.
- **The previous record's attribution was wrong and is superseded.** The file that was written held above-ground biomass 6.7 % HIGH (4,030 against 3,777 gC/m²), not 50 % low; the loss happened during the model run. So adding biomass to the donor-matching objective — the previously recommended next step — would have chased a bias that was not there.
