## 2026-09-08 — D1: the perturbed `.clm` writer, and what the model did with it

### Reading the C before writing anything

The whole of D1 turned on three things that are only knowable from the source, and all three would
have been silent failures if guessed:

* **A subset forcing file is legal.** `openclimate.c:207-219` seeks by
  `(startgrid − header.firstcell)` and strides by `header.ncell`, and `openinputfile.c:145` gates
  the range on `firstgrid`/`nall`, which come from `startgrid`/`endgrid`. So `firstcell = <cell>,
  ncell = 1` works while the grid and soil inputs stay global. That single fact is the difference
  between a 1.3 GB pilot corpus and a 450 GB one.
* **`shuffle_climate` is TRUE**, so `binfmt.md` §3's deterministic-cycle formula was the branch
  that is not taken. Fixed. The useful corollary is that the draw sequence depends only on
  `random_seed`, so two arms at the same seed see the same climate years — which is what makes a
  paired single-cell comparison worth anything.
* **The ground truth's spin-up passes no `-D` flag at all.** Its `--comment` field claims
  `-DFROM_RESTART` and is stale. So `inherit_startyear` was 0, not 200 — which falsifies the
  mechanism `20260908-D-spinup-is-not-converged.md` proposed for the late rise in its trajectory.
  That record flagged the attribution as unestablished, so this costs it nothing but the guess.
  Our own runs print `inheritance after 0 yrs`, so it is read off the model rather than inferred.

Also read `waterstress_tree.c:36` → `getvpd.c:38` and found that LPJmL-FIT's tree water stress is
the *only* consumer of the humidity input outside SPITFIRE, and that it derives relative humidity
with a specific Bolton form at 1013.25 hPa. So "hold relative humidity fixed" was implemented
against **that** formula rather than a textbook one — otherwise the test would pass while the model
saw a drifting humidity. It comes out exact: `q' = q·esat(T')/esat(T)` leaves the model's own
relative humidity bit-unchanged, verified to 1e-12 on every written value.

### What the writer guarantees

A neutral design point is a *structural* no-op — every axis behind an explicit `if` — so a
zero-perturbation file reproduces the source bytes exactly. That is the proof, and it passes on all
five variables against the real 11.7 GB inputs. Everything else follows from it: if the identity
point is exact, a perturbed file differs from the source in exactly what the design says.

### Two bugs worth remembering

**The nested-heredoc line continuation.** The manifest runner was first written as a `$(cat <<EOF)`
inside an `sbatch <<EOF`. A `\` continuation did not survive both rounds, the member command became
an empty string, and SLURM reported `exit=127` with no other symptom. Rewritten as a runner *file*
built with a quoted heredoc; its inputs arrive as exported variables. It is also now left on disk
next to the manifest, so a failed member can be rerun by hand.

**`srun` ate the manifest.** `srun` forwards its stdin to the task, and inside
`while read … done < manifest` that stdin is the manifest. Eighteen of 25 lines were swallowed:
seven members ran, the job exited 0, and the summary line said **"7 of 7"** — because the expected
count came from the same starved loop that had been shortened. Both halves matter. The launch fix
is `< /dev/null`; the *reporting* fix is to take the expected count straight off the file, so an
under-launch is loud instead of self-consistent. A green job that quietly did 28 % of the work is
exactly the failure mode the campaign ledger exists to catch, and it nearly wasn't.

### The science, and where it left me uncomfortable

I wrote the expected direction per biome into the analysis script *before* the runs finished, which
turned out to matter, because two of five cells went the other way. Boreal Siberia lost carbon
where cold-limitation says it should gain; the Sahel gained ~50 % where heat and water say it should
lose. Mediterranean Iberia and the Amazon behaved as expected, Iberia monotonically.

My first instinct was that the fixed-humidity rule was doing it — it is the most aggressive thing in
the design, since holding relative humidity makes vapour-pressure deficit climb steeply with
temperature and that deficit feeds mortality directly. So I ran an attribution arm: the same +4 K
with specific humidity left alone, relative humidity allowed to fall. It moves the answer by one to
two points at four of five cells. The rule owns almost none of the response. That was worth six
minutes of compute and it changes what can honestly be said: these are LPJmL-FIT's own numbers.

What I could *not* explain, and did not try to write around: the Amazon is non-monotone. −36 % at
+2 K, −97 % at +4 K (a flat dead cell, 667 gC/m², from the first hundred-year block), and back to
~35 % of control at +6 K. I checked the obvious wiring — the three forcing files differ only in the
temperature increment, everything else byte-identical, and the +6 K run's log names the +6 K file.
So it is the model. It goes to line X as an open question rather than into a story I can't support.

The Sahel is more interesting than "wrong": its two arms are on entirely different transients, the
control still climbing steeply at year 1000 while the warmed arm peaked early and is falling. That
is the non-converged spin-up showing up as a *comparison* problem, not just a labelling one. The
target is still well defined — it is the state the protocol reaches — but equilibrium intuition is
not a valid check on it, and I should stop reaching for equilibrium intuition when reading these.

## 2026-09-09 — D2: the corpus is real, and the base I started from was 45 commits stale

The pilot corpus ran. 6,000 spin-ups, all 6,000 with the model's own completion line, 337 core-hours
against an estimated 670. I want to record what nearly went wrong instead, because the runs were the
easy part.

**The session's real hazard was that I almost worked for hours on a stale base.** The handoff said
D2 was unblocked and nothing stood in the way, and it was right about that — so the temptation was
to go straight to code. I did go straight to code, and only when I tried to commit did I look at
`main` and find it 45 commits ahead with three unread inbound messages in my own state file. Two
were gate debt that would have blocked the merge whatever I built on top; one told me to delete a
warning from my handoff that the owner had already settled and asked never to be re-asked. Worse,
one of the two blocking warnings in my own handoff — the broken escape hatch on the login-node guard
— had been *fixed on main* while I was working around it. So I spent effort routing around a bug
that no longer existed, and my STATE.md was telling a future session to ask for a fix already made.

The lesson is not "rebase first" as a chore. It is that a handoff is a snapshot of what one line
knew, and its warnings decay fastest of all its content — they are written at the moment of maximum
frustration and nothing makes them expire. Both of mine were stale within a day. I have written the
new ones with the same doubt: they say what is measured, and the one process complaint goes to the
changelog where an integrator will actually see it rather than sitting in my file forever.

**The design decision I am least sure of** is one cell per tile. It covers all 164 populated 15°
tiles, which is what makes a blocked fold mean anything, but it buys that coverage by giving up
within-tile replication entirely — so the corpus cannot separate "the model interpolates in space"
from "the model responds to climate". I chose coverage because the roadmap's rule says stratify by
the tiles, and because rung 1's decisive null is the same-cell baseline, which is per-cell and
unaffected. But I have said so explicitly in the record rather than presenting it as free, and if
line X needs the separation the mid tier should put four cells in fewer tiles. That is a real
trade-off and I do not think it has an obviously right answer at 200 cells.

**Two bugs the new tests found, both of the kind that fails nowhere near itself.** Adding a
dataclass to a script that gets loaded by path broke two unrelated real-data tests with an
`AttributeError` inside `dataclasses.py` — because none of the three loaders registered the module
in `sys.modules`, and `from __future__ import annotations` makes every annotation a string that
`@dataclass` then cannot resolve. And the maximin fill tested exhaustion with `isfinite`, which is
false for the `+inf` of an unvisited candidate, so starting from an empty set selected nothing at
all and reported success. Neither would have been caught by using the code as production uses it;
both came from a test that used it slightly differently.

**And I misdiagnosed something for a few minutes.** Six guard tests went red after my changes and I
started reading my own diff for the cause. It was my shell: I had exported `ALLOW_LOGIN_HEAVY=1`,
the hook allows unconditionally when it sees that, and the tests inherit the environment — so every
must-deny case failed at once, which reads exactly like "you broke the guard". A test of a deny rule
has to control the thing that disables the rule, so it now strips all three overrides. Worth
remembering that the most confusing failures this session were both environment, not logic.

**What I deliberately did not do:** decode the 6,000 restarts. It is the obvious next step and I had
the time, but it is a separate deliverable with its own failure modes — a single-cell restart is one
record, not a slice of the 119 GiB file, and v0's reader was written against the latter. Starting it
badly at the end of a session is worse than handing it over cleanly. The corpus is 6,000 files and I
have said so in every place the number appears, rather than calling it a corpus and letting the next
session discover the difference.
