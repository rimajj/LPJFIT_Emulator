### Added
- **A tool that could make fresh reference runs of the original model at every location is built and tested, but it is parked and will not be launched: on 2026-09-24 the owner decided that no new all-location reference runs are needed.** The reference is the runs already on disk: the stored 1,000-year settling-in run (using only its years before carbon dioxide starts to rise), and the stored low- and high-emissions scenario runs, which run only from 2020 to 2100 and so are not treated as a settled forest. The tool is kept, and marked as parked in its own text and in every stage's output, because it is tested end to end and its small trial (next point) proves that a one-location rerun reproduces a training simulation exactly. What it would do: run the original model's full 1,000-year settling-in at each of the 67,420 land locations under three climates (1970–1999 observed, and 2071–2100 under the low- and high-emissions scenarios), twice with different random seeds, exactly the way the training simulations were made — cutting each location's 30 years of climate out of the global files, writing the model's settings, listing the runs in balanced batches, checking every file before anything is spent, judging each run by the model's own "finished successfully" line, and producing a table with the training table's columns. Had it been run, the projected cost for both seeds was about 24,200 core-hours of model time (25,500 charged), about 0.9 TB of disk and about 3.9 million files; that projection was never tested at scale.
- **A one-location rerun with the tool reproduces the training simulation to the byte.** A small end-to-end trial ran 8 locations × 3 climates, all 24 to completion. For the 3 of those locations that are also in the training set (central Germany, the Amazon, Siberia), the climate files and the final forest state are byte-for-byte what the training run produced, and the decoded table row matches the training row in every forest, climate and location column; only the row's labels and the five climate-change settings (left empty for these runs) differ. So they are the same simulation, not just similar ones — 3 locations, today's climate, one seed. The trial was also the test of the cheaper batching below: 24 runs through 6 processors used 93 % of what was charged, against 53 % the old way.
- **The model's two program versions were tested against each other for the first time, and gave byte-identical results for one location and one year.** Part of the stored reference data came from an older build of the original model (5 February) and the training simulations from a newer one (12 August). The difference was believed harmless from reading the code, but had never been tested. Running one forested location for one year from the same starting state, the two builds wrote identical final states, identical per-tree output and identical carbon and water totals, and a repeat of the newer build matched too. It covers one location and one year of an ordinary run, not every code path, and not the third (21 July) build. Written up in decision record `20260923-D-the-two-builds-write-byte-identical-restarts`.

### Changed
- **Batch jobs of many short model runs can now be charged for roughly the time they actually use.** Before, every run in a batch held its own processor until the slowest one finished, so the 6,000 training simulations were billed for 1.9 times the computing they used. Asking for fewer processors than runs now makes the batch start each next run as soon as one ends. Without that setting a batch behaves exactly as before, one processor per run, and a single (non-batch) run keeps the processor count it asks for. The ledger that tracks jobs now also records the estimated cost, the deadline for collecting results, and two optional output settings that change what the model writes, and it is written with the cluster's own Python, so the record of a queued job can no longer be lost to the login node's older Python.

### Fixed
- **Runs of the older model build would have been recorded as failures even when they succeeded.** The model announces success with a line starting with its own file name, and the older build's file has a different name, so the check that looked for the newer build's name could never match it. The check now uses whichever build was actually run.
- **"The 54,020 locations with trees" now has a precise, reproducible definition.** It is the set of locations with at least one living tree (not grass) in the older per-tree output table, which leaves out trees under 5 m. Counting every location in that table gives 63,119, because it lists grasses too. The reference plan marks all three ways of counting side by side (56,986 locations with any tree at all in the settled state, 52,198 with a tree at least 5 m tall, and the 54,020).
