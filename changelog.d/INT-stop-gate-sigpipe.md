### Fixed

- **The Stop gate was unsatisfiable: it blocked every session that committed on a work line, including the ones that DID refresh their handoff.** `session-end-gate.sh` checked `git log origin/main..HEAD --name-only --format=%B | grep -qE "lines/$LINE/STATE.md|NEXT: unchanged"` under `set -o pipefail`. `grep -q` exits at its first match; `git log` still had kilobytes queued behind it (15,841 bytes over the eleven commits on `line/X`), so it took SIGPIPE; `pipefail` promoted 141 to the pipeline's status; the `if` went false and the gate reported a missing handoff to a session that had just written one. The advertised `NEXT: unchanged (<reason>)` escape hatch sat inside the same `grep` and failed identically, so there was no way out at all. The check now captures `git log` into a variable and greps the variable — no pipeline, no SIGPIPE.
- **It punished the correct behaviour hardest, which is why it went unnoticed as a bug and was written up as an immovable fact of life.** `git log` emits newest-first, so refreshing the handoff in your LAST commit puts the match at the very top of the stream and makes the early exit certain. A session that refreshed its handoff late and committed nothing after would sometimes pass; a session that did the tidiest thing never would. Line T's `STATE.md` had carried "the Stop gate CANNOT be satisfied — refresh the handoff because it is right, then ignore the block" as a standing gotcha.

### Added

- **`tests/test_session_end_gate.py`** — five cases run against the hook FILE, including the exact regression: ~50 KB of older commits with the handoff refreshed in the newest one. Verified in both directions (it fails on the pre-fix hook with `block != allow`, and passes on the fixed one), and it still pins the gate actually blocking when the handoff genuinely was not refreshed, so a fix that merely returns 0 cannot pass.
- **A warning on the sibling pipeline in `path-guard.sh`.** Its `head -15 "$FILE" | grep -qi 'status.*accepted'` is the same shape but is SAFE, because it is ONE write of ~667 bytes that lands before `grep` can quit — verified 12/12 against a real accepted record. Swapping that `head -15` for an unbounded reader would make the accepted-decision-record guard fail OPEN with no message, so the constraint is now written down where someone would make that change.
- **A correction to the threshold, because the wrong version of it is actively dangerous.** The first write-up of this fix explained the safety of `head -15` by the 64 KB pipe buffer — "a small writer finishes before `grep` quits". That reasoning invites "my writer emits 30 KB, which is under 64 KB, so I am safe", and that is false: re-measured on `line/X`, the broken gate took SIGPIPE **6/6 at 15,841 bytes**, a quarter of the buffer. It is a race against a `grep -q` that exits on its FIRST match, not a buffer-capacity question, and newest-first output puts that match in the first few lines. The comments in both hooks and the test now say so.

### Changed

- **A note on verifying this class of bug: it does not reproduce interactively.** The identical pipeline typed into an interactive subshell returns 0 six times out of six; run as a script — which is how a hook runs — it returns 141 six times out of six. Checking by hand at a prompt reports the bug fixed when it is not. Execute the hook file.
