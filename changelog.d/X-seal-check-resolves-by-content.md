### Fixed

- **The check that proves a pre-registration existed before its run no longer fails on seals nobody touched.** E12 took the `seal_commit` hash recorded in `experiments/registry.jsonl` and asked git whether it was an ancestor of the first result commit. But the runbook requires rebasing onto `main` before merging, and a rebase rewrites every not-yet-merged commit on the line — the seal commit included — so the recorded hash names an object on no branch, ancestry is false for everything, and the gate reports a violation against provenance that is entirely intact. It fired three times in one session on three correctly sealed experiments, and each was silenced by appending a correction row to an append-only ledger. A real integrity gate that cries wolf is one people learn to route around, so the workaround, not the symptom, was the bug. **E12 now resolves the seal by CONTENT** — the earliest commit whose `preregistration.yaml` hashes to the recorded `prereg_sha256`, an identifier a rebase cannot change — and no check reads `seal_commit` any more. It stays in the ledger as a breadcrumb, and `tools/seal_experiment.py` now says in its own docstring that it must **not** be corrected when it goes stale.

- ⚠ **This is stricter than what it replaced, not a relaxation.** The old check never opened the commit it named: it proved only that *some commit id* preceded the result, so a `seal_commit` pointing at any early commit passed — including one that never contained the pre-registration, or contained a different one. The new check cannot pass unless the sealed bytes are genuinely in history before the results. It therefore catches a case the old one was blind to: a pre-registration **edited after sealing** now leaves no commit carrying the sealed bytes, and E12 says exactly that. Verified both ways on the live repository — with the orphaned hash restored the gate is green where it used to fail, and with the sealed hash tampered it fires where it used to pass. Content resolution also independently derives the same commits the three hand-written correction rows had recorded, so it reproduces the manual forensics rather than merely being green.

- **A shallow clone is now reported as "cannot verify", not as a violation.** "Not fetched" is not "not sealed", and a checker that cannot run must say so rather than report a finding it did not measure — the same lesson already learned twice in the hooks. CI is unaffected; the experiments workflow already checks out with full history.

### Added

- **`tests/test_seal_provenance.py`** — six tests, each building a throwaway git repository, with the rebase case performing a **real** rebase rather than simulating one. It pins that the recorded hash is orphaned and the content still resolves, that a seal genuinely following its results is still caught, that sealed bytes never committed are caught, and that the *earliest* carrier wins so a later touch cannot move the seal past its own results — two of them through the real `check_append_only` code path, because a correct helper proves nothing about the check meant to call it. The rebase test also asserts the **old** logic fails on the same input, so it cannot quietly stop reproducing the bug.
