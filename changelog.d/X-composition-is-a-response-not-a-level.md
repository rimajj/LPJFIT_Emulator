### Added

- **Species composition becomes a scored quantity, and the acceptance band gains an additive floor so that it can be one.** The owner decided on 2026-09-14 that the seven `pft_frac_*` columns join `SCORED_CONJUNCTIVE` at corpus v2, overturning line X's earlier answer of "no" — the copied composition is plausibly on the critical path for the central failure, which outranks a scoring preference. But the measured obstacle that produced that "no" does not go away; it becomes load-bearing, so the band for those columns becomes `max(relative_spread × |truth|, ABS_FLOOR)`. A relative tolerance on a **bounded fraction** is a category error, and without the additive term the new columns would make the statistic anti-correlated with the capability they were added to measure. ⚠ **`ABS_FLOOR` must not reuse the existing `FLOOR = 0.10`**: composition shares are strongly skewed (median non-zero share **0.0776**), so a floor of 0.10 would make **53.9 % of genuinely present tree types indistinguishable from absent**, trading a metric degenerate at zero for one blind to most of the signal. The workable magnitude is of order 0.01, and the value itself must be **measured** from the model's own absolute two-seed spread and pre-registered — which makes line D's second pilot seed a prerequisite rather than a nice-to-have. **v2's build is unaffected, so D is unblocked either way.** Records: `docs/decisions/20260914-X-composition-is-scored-and-its-band-must-become-additive.md`, superseding the decision of `20260910-X-composition-is-a-response-not-a-level.md`.

### Fixed

- **The remedy asserted in the synthesiser's own header comment was the wrong one, and adding those columns to the band test would have been perverse rather than merely strict.** `src/vegemu/models/synth.py:56-61` states that composition "becomes predictable as soon as those columns are added to the scored set". Measured, it would not. The acceptance band is `max(10 %, spread) × |truth|`, so **a truth of zero yields a band of exactly zero and only an exactly-`0.0` prediction passes** — verified against the shipped functions, where predictions of `1e-9`, `0.01` and `0.05` all miss. Composition is structurally zero: in `corpus/pilot-v1` (6,000 rows) **45.6 % of cell–PFT pairs are exactly zero, all 6,000 rows hold at least one zero, and no cell holds all seven PFTs** (median 4 of 7). So every row would carry at least one zero-width band, the 22-way conjunction would become a 29-way one scoring ~0 for any continuous predictor whatever its composition skill — **while the template-copying synthesiser, which reproduces the template's zeros exactly, passes all seven trivially.** The statistic would be anti-correlated with the capability it was added to measure, hence `invalid` under invariant 3. That is why the columns cannot simply be appended to the scored set: the additive floor above is what makes the owner's decision implementable. This is the third time deriving the nulls before designing the statistic has caught a dead metric before sealing rather than after.

- **Two long-standing "verdict metrics block is STALE" open loops were false, and the hook that reported them cannot be cleared by the command it suggests.** `.claude/hooks/session-open-loops.sh:27` calls bare `python3`, which on the login node is 3.9 and has no `tomllib`; `tools/_common.py` imports it at module scope, so the checker dies with `ModuleNotFoundError` and exit 1 before reading a single verdict, and `2>/dev/null` discards the traceback. The hook maps that non-zero exit to one specific meaning — "the block is stale" — so **an interpreter crash is rendered as a substantive finding about the repository.** Under the project interpreter (`config/paths.yaml`) both verdicts report *up to date* and re-rendering them changes no byte. This is a fourth instance of one shape already recorded three times: a guard whose input is not what it guards. It also **masks a genuinely stale verdict**, which is indistinguishable from it. Diagnosed, not fixed — `.claude/hooks/**` is integrator-exclusive. Verified in passing that the commit guard fails **closed** rather than open (`run()` treats a non-zero exit as a finding, so no check is silently skipped), and that CI is unaffected because every workflow pins Python 3.11. Record, with the suggested fix: `docs/decisions/20260910-X-the-open-loops-hook-misreads-a-crash.md`.
