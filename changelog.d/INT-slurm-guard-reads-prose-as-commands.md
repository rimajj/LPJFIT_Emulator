### Fixed

- **The safety check that keeps heavy computation off the shared login machine no longer refuses commands that merely *mention* heavy computation.** It decides by scanning a command's text for keywords, so in a project whose subject matter is corpora and training, ordinary sentences set it off: sending a note to another work line whose body quoted `corpus/state.py` was refused as a heavy job, and a commit message naming the job-submission wrapper was refused as an attempt to bypass the job ledger. Neither command runs anything at all. The rules now read the command with the *arguments of text-carrying options* removed — `-m`, `--message`, `--body`, `--subject`, `--reason`, `--allow-red`, which is every such option in the repository — so the guard stops reading other people's prose as instructions.
- ⚠ **The reason this was worth fixing is not the annoyance.** The workaround was to prefix the override that switches the guard off onto ordinary `git` and note-sending commands. That is worse than what it solved: it trains the habit of disabling the guard on commands the guard was never meant to catch, and the habit does not reliably stop at the harmless ones. This is the third instance in this repository of a single fault — a guard matching text that is not what it guards — after the two already fixed in the commit checker.
- ⚠ **Stripping is by OPTION and not by quotation, deliberately.** The commit checker strips every quoted string, which is right there and wrong here: `python3 -c "import torch; …"` is a quoted string that *is* the program, and is exactly what this check exists to refuse. `-m` is the one ambiguous case — a message after `git`, but a *module* in `python3 -m torch.distributed.run` — and is settled by whitespace, since a commit message has spaces and a module name never does. Both are pinned as must-refuse cases, so widening the option list turns one of them red.
- ⚠ **Not fully closed, and honestly so.** Text that is not an argument to one of those options is still scanned, so a keyword inside a shell loop literal or a heredoc body still trips the check — that happened while verifying this very change. The override still exists for those, and it is still the right tool there.
- Fails safe in both directions: a command that cannot be parsed keeps the old, broader matching, and so does an empty or crashed parse — neither can widen into a total bypass. The parse is a second process on every command (~30 ms) rather than being folded into the existing one, precisely because the existing one fails *open*.
- Reported by line X, who also stated the preference that it be fixed rather than documented. 28 cases verified; the four newly-allowed ones were confirmed to fail against the previous version, so the test is not passing vacuously.
